# 2. Review method

For each `OPS-UPD-001...007`, ask:

1. Is a participant/customer/release/business right still undefined or contradictory?
2. If yes, what is the highest authority that must change?
3. Is current Architecture/Domain ownership already sufficient?
4. Which details are truly Product semantics versus JIT/proof/provider/expert work?
5. Does any delta depend on another being settled first?
6. Can the change be reviewed and superseded independently?

The default is **minimum necessary authority change**, not broad harmonisation.

# 5. Why `OPS-UPD-004` must go first

The other deltas are missing policy. `OPS-UPD-004` is worse: current governed text conflicts.

The focused v0.11.0 pass established:

```text
DEC-055:
first answer / attempt begins
→ consume / mark used

versus

current Product matrix + FP-003 Roadmap:
successful digital assessment delivery
→ consume
```

The minimum safe repair is an explicit Decision/Product successor that:

- supersedes/refines the attempt-begin consumption wording;
- treats first-answer/attempt start as a held/claimed availability boundary if that is the approved rule;
- keeps the credit commercially unconsumed until the governed successful-delivery event;
- defines terminal expired/unrecoverable non-delivery treatment;
- preserves technical-failure recovery without duplicate right/result/consumption;
- keeps refundability separate.

This repair should be independently reviewed before any operator command matrix can rely on assessment-credit recovery semantics.

# 6. Minimum Product promotion surfaces

## 6.1 `OPS-UPD-001` — pilot admission

Preserve current hard facts: first pilot maximum 50; 10 and 25 are deliberate review/progression points; paid demand requires verified actual payment; headcount is human participants.

Promote only the missing admission lifecycle: exact 10/25 closure, provisional capacity claim, verified-payment admission, known failure/unknown outcome, pause/in-flight/late success, historical membership, invalid-from-inception correction/backfill.

Do not freeze table/row/lock/provider implementation in Product Law.

## 6.2 `OPS-UPD-002` — duplicate collection / partial loss

Compose with `DEC-300`; do not reopen full reversal.

Promote only:

- one accepted purchase may be satisfied once;
- extra genuine collection creates no extra right;
- full excess remains owed until made whole;
- failed/ambiguous provider execution does not erase the obligation;
- no double economic correction;
- partial provider loss is financial truth, not component identity;
- only governed NewYou evidence may identify the affected component/right.

## 6.3 `OPS-UPD-005` — pre-first-fulfilment Plan change

Preserve successful delivery as consumption boundary and immutable generation history.

Promote only the customer-right question: may the same unconsumed right fund replacement, does generation stage matter, what happens to the original right if a new purchase is required, and what minimum repeated-change/correction rule is needed.

## 6.4 `OPS-UPD-006` — export + Full Deletion

Do not promote until legal/privacy review validates the participant promise.

The promotion should cover only predating export continuation, exact successful handoff, irreversible-deletion termination if undelivered, participant-held copy treatment, and deletion-cancellation resume. `OQ-032` remains operational.

## 6.5 `OPS-UPD-007` — General Wellness clock start

Compose with `DEC-308`; do not select a provider/channel.

Promote one qualifying communication boundary, one-window/no-reset semantics, explicit exclusion of internal intent/provider acceptance/open-read telemetry as independent clock starts, and deadline-created refund obligation.
