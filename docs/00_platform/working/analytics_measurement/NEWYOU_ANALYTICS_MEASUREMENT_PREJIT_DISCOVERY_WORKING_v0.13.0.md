# 4. Phase 7B — required JIT Domain Dossiers

## 4.1 Domain dossiers resolve only Domain-owned truth

A required 7B dossier may resolve or validate the lifecycle semantics owned by that Domain, for example:

- which authoritative state or transition exists;
- which timestamp is authoritative for that Domain fact;
- how correction/replacement/reversal works in that Domain;
- how retries/idempotency/deduplication affect that Domain truth; and
- which invariants prohibit a proposed metric interpretation.

A dossier must not become the owner of the entire cross-domain metric merely because its facts are important to the metric.

## 4.2 Cross-domain metric choices remain outside a single source dossier

Questions such as:

- which lawful business population should be the metric denominator;
- which of several source-domain facts should qualify for a Product gate;
- which prospective window should govern the aggregate; or
- how multiple source-domain truths combine into one gate definition

are metric-contract decisions constrained by Product/Decision/Roadmap law.

A source-domain dossier supplies authoritative constraints and facts. It does not gain cross-domain Product-metric authority.

## 4.3 Do not manufacture dossiers

If the future Gate Manifest determines that current Domain Law already supplies the needed source semantics and no JIT dossier is required, Pass 13 does not create one.

Conversely, if the Gate Manifest classifies a dossier as required, the metric closure path may not bypass it by citing this Pre-JIT stream.

## 4.4 Conditional dossiers

A conditional dossier that could materially change a metric semantic cannot remain silently unresolved when 7C freezes that metric.

Before 7C, it must be explicitly adjudicated under the normal Feature Pack process:

- required and completed; or
- not required / non-blocking for the specific metric decision, with the authority basis recorded.

Pass 13 does not perform that adjudication.

# 6. Phase 7C — Final Feature Pack Contract

## 6.1 7C is where the complete metric contract must be development-entry visible

The approved FP-006 Final Feature Pack Contract must carry the resolved metric contract rather than forcing an implementer to reconstruct it from multiple dossiers.

For each metric in scope it should make the final governing semantics explicit:

- numerator;
- denominator;
- qualifying event/condition;
- measurement window;
- exclusions;
- missing-data treatment;
- cohort;
- metric-definition version;
- metric-specific temporal/retry/recovery/replacement/restatement rules where material;
- authoritative source Domain references;
- prospective effective point; and
- fail-closed behaviour.

7C may cite the relevant dossiers and authority as evidence, but a chain of links is not a substitute for the final explicit contract.

## 6.2 7C must preserve source ownership

Carrying a source semantic into 7C does not transfer ownership of that truth to the Feature Pack or Analytics.

The Final Feature Pack Contract defines how the Feature Pack consumes authoritative truth for its metric. The owning Domain remains authoritative for that truth.

## 6.3 Paid-participation boundary

If a required paid-pilot metric contract remains unresolved:

```text

=> NOT DEVELOPMENT-ENTRY READY
=> NOT RELEASE-READY
```

This does not automatically create a broader stop for unrelated internal preparation if the governed Feature Pack scope and Gate Manifest lawfully permit such preparation.

Any allowed partial progression must explicitly exclude the blocked paid-participation capability rather than treating the metric as implicitly resolved.

Pass 13 does not decide whether a future FP-006 partial-scope path is permitted; it preserves the existing gate mechanism.

## 6.4 Other metric obligations are not erased

Pass 13 focuses on unresolved semantics for `ANL-METRIC-003..006`.

It does not weaken the accepted requirement that `ANL-METRIC-001` and `ANL-METRIC-002` also need their complete prospective JIT contract before first paid participation.

# 7. Architectural-proof classification and proof execution

Proof classification occurs downstream of the approved 7C contract.

The selected proof path — when governance later chooses `REUSE_EXISTING_PROOF` or `NEW_TRACER_BULLET` — must treat the frozen 7C metric contract as an input, not as something to redesign.

Architectural proof may establish that the chosen architecture can:

- preserve source-Domain authority;
- correlate the required facts safely;
- handle relevant concurrency/retry/idempotency boundaries;
- preserve version/cohort provenance;
- derive the metric without hidden business authority in Analytics; and
- fail closed when required inputs are unavailable.

Architectural proof must not:

- choose a missing denominator;
- redefine a qualifying action;
- move a measurement window;
- invent a replacement/refund/reversal classification; or
- relax a source-domain invariant to make implementation easier.

A failed proof can expose an upstream contradiction. It cannot repair that contradiction by changing the metric contract inside the proof artifact.

---

# 8. Implementation, vertical slices and horizontal hardening

Once development entry is legitimately reached, implementation is downstream of the frozen contract.

Implementation-level choices such as event names, schemas, jobs, projections, indexes, query shape and dashboards must implement the contract rather than become hidden semantic authority.

Vertical slices must prove the real cross-domain path they implement.

Horizontal hardening may strengthen:

- retry handling;
- duplicate/reordered evidence behaviour;
- recovery;
- reconciliation;
- observability;
- performance; and
- operational resilience.

But hardening may not silently change the business population, qualifying condition, time window or lifecycle meaning of the metric.

If implementation reveals that the approved metric contract is inconsistent with higher authority or cannot be implemented without violating Domain Law, work must stop at the correct upstream authority level.

---

# 9. Release readiness

Release readiness verifies that the approved contract and its downstream evidence are sufficient for the paid-participation decision.

For the metric-contract part of readiness, the reviewer must be able to trace:

```text
current Product / Decision / Roadmap requirement
    -> approved 7C metric contract + version/effective cohort
    -> required source-Domain dossier / authority evidence
    -> selected architectural-proof classification and proof result
    -> implementation/hardening evidence
    -> analytical derivation / completeness evidence
    -> release decision
```

Release readiness may discover that evidence is missing, stale or failing.

It may **not** repair the result by:

- changing the denominator;
- moving the cutoff/window;
- excluding inconvenient members;
- substituting Analytics ingestion time;
- rewriting the definition for the observed cohort; or
- treating an unresolved contract as a measured `0%`.

If the required contract/evidence is not sufficient, the paid-participation decision remains NO-GO.
