# FP-001 Identity & Access JIT dossier v0.3.0: resend successor

This semantic successor amends the Identity & Access JIT dossier v0.2.0 at `docs/00_platform/working/FP-001_IDENTITY_ACCESS_JIT_DOMAIN_DOSSIER_WORKING_v0.2.0.md`. It inherits that dossier except where this document explicitly changes resend operation representation and its lifecycle. The predecessor remains at its historical Foundation Full pin; its current-status statements describe the prior certification, not the live route. The current authority router selects this successor. This candidate requires independent review and does not claim certification or authorise WELL-51 implementation. Product, Architecture, Domain and Roadmap law remain unchanged.

## Representation and ownership

P8-05 locks one independent resend operation per logical request, replay of its safe result and an Identity-owned resend audit trail. The predecessor fixes `RegistrationOperation` to registration and Token to proof. Expiry cleanup may expunge Token rows. Neither challenge presence nor a mutable Account field can therefore preserve multiple earlier resend bindings and their audit after later resends and cleanup.

* Account plus Token alone is rejected. A single current Account field loses earlier operations; accumulating an independent history on Account would itself introduce a separate durable operation representation. Token cleanup destroys the necessary history. Token remains the sole proof-token store.
* Generalising RegistrationOperation is rejected. Its binding, password verifier, expiry, account relationship and neutral duplicate registration outcome have registration-specific meaning. Making it a shared ledger would change that meaning and couple unrelated lifecycle and privacy rules. `RegistrationOperation` remains registration-only.
* Select a private Identity-owned `ResendOperation` Ash Resource, backed by PostgreSQL, with purpose-specific Identity actions. It owns immutable resend request binding, terminal safe result, minimum resend audit and durable anti-rebinding. It is not a token, Account, central Audit evidence or Communications delivery record. It adds the ninth Identity physical Resource to the predecessor's eight-resource set. No generic operation ledger, public CRUD, parallel Repo write API or new Domain is authorised. The Resource name describes the selected semantic purpose; internal fields and action names are JIT choices subject to this contract.

Identity owns challenge and operation truth. Communications owns each `MessageIntent`, protected-delivery envelope, attempts and delivery. P8-10 owns subsequent discovery, scheduling and delivery execution. An ordinary accepted resend creates no central Audit `EvidenceObligation` or Audit durable schedule. No delivery status establishes verification.

## Binding, admission and replay

The browser creates a fresh opaque operation ID for each explicit resend and reuses it only for retries of that logical request. The ID is not a credential or proof. Identity binds it immutably to the canonical request inputs, account and source context needed to distinguish a changed request. Comparison must not retain raw request data or require a bearer. A keyed, domain-separated fingerprint with an independently managed key is a possible JIT mechanism; unavailable comparison material fails closed. PostgreSQL uniqueness covers every used ID including tombstones. An operation ID is globally unique within this resend purpose, not scoped so that another account can reuse it.

Only the Identity owner action may admit a request. It applies current resend eligibility and applicable abuse controls without exposing account existence. The browser ID alone cannot authorise an account lookup or mutation. Unknown, verified, closed, expired or otherwise ineligible accounts receive a neutral public response. A rejected admission must not create a challenge, intent or envelope. If a terminal neutral result is committed for an admitted ID, it is bound and replayed under the same rules as an accepted result; no account existence is disclosed. A failure before commitment leaves no binding or consequence and an unchanged request may retry the ID. Corrected input uses a new ID. Changed-input reuse of a bound ID fails closed without mutation or a new consequence.

A committed matching replay returns its original safe, neutral result while the binding is live, including after a later resend or Token cleanup. It does not issue, replace or reactivate a challenge and does not create another intent or envelope. In particular, replay never supersedes a newer challenge. After binding expiry or applicable invalidation, a tombstone rejects reuse safely rather than reconstructing the prior response. It never creates a new logical resend. A later explicit resend uses a distinct ID and may be accepted if current eligibility permits.

## Lifecycle and arbitration

The durable states are `bound` with an immutable terminal result and `tombstoned`. Admission is an in-transaction decision, not an independently committed pending state. For an eligible request, the owning action binds the ID and commits `accepted` only with the complete acceptance boundary below. A committed neutral ineligible outcome, where admission binds it, is a separate terminal result. Both are immutable while bound. Replay and changed-input rejection do not transition the record. Expiry or applicable Account invalidation transitions bound to tombstoned. Tombstones are terminal and never become bound again. No worker, cache or process state decides any transition.

For an accepted resend, one PostgreSQL transaction through the owning Ash interfaces serializes the Account and verification purpose, rechecks current eligibility, supersedes the current active verification challenge, creates exactly one replacement Token challenge, binds the accepted operation and its Identity audit, and creates exactly one Communications `MessageIntent` and one protected-delivery envelope. All commit or all roll back. There is exactly one current active verification challenge after each accepted transition; an Account that is closed, verified or otherwise invalidated may have none. A uniqueness/conditional-write invariant and Account-purpose serialization must cover initial issuance, resend, proof consumption, closure and invalidation, not resend alone. No provider I/O or Communications job is part of this transaction.

Concurrent same-ID requests use the database unique constraint and transaction arbitration: one can commit, matching losers read the committed safe result, changed-input losers fail closed, and a rolled-back contender leaves no partial consequence. Competing distinct IDs serialize on the Account and purpose; each eligible committed acceptance replaces the challenge current at its serialization point. The later committed transition owns the sole current challenge. A failed or retried transaction rechecks all guards; it cannot use a stale challenge decision. Earlier accepted replay is read-only even after this sequence.

Account closure or invalidation atomically prevents subsequent acceptance and invalidates current challenges under Identity's existing lifecycle. It also invalidates live resend bindings as applicable; retries then fail closed. Expiry, supersession or expunging a Token cannot delete or release the operation ID or its retained audit evidence. A mistaken revocation or other correction is a separately authorised, new operation using a new ID; never rewrite an accepted event or reactivate its old challenge. Record a correction relationship only where permitted by the retention policy. An inconsistent partial state is an integrity incident: deny further effects, reconcile through owning Domain interfaces and preserve truthful provenance. Never infer or fabricate a missing acceptance from Communications delivery state.

After crash or restart, PostgreSQL's committed state decides whether acceptance occurred. Retry the unchanged request to recover its safe result; rollback leaves no accepted effect. Communications independently discovers the committed intent under P8-10. Recovery never repeats Identity acceptance to recreate a lost job or envelope. Backup/restore discrepancies require reconciliation before further affected sends; no process-local lock is an authority.

## Retention and audit

Keep the live immutable binding and safe result for its approved category-specific replay retention, subject to earlier applicable invalidation. A retry does not renew the period. No new duration is selected here: Privacy & Consent owns approved policy, legal holds and disposition. Until that policy is decided, do not silently discard required live replay or audit evidence. The implementation must resolve the applicable retention policy before production release, without inventing a legal duration.

After the approved live period or invalidation, remove the live binding's request comparison material, key version, account/source association and detailed replay result, subject to a valid hold. Separately retained audit fields follow the audit retention policy below; the binding cleanup must not erase them prematurely. Retain a permanent anti-rebinding tombstone containing only the opaque operation ID and minimal tombstone state; it has no Account, email or participant lookup. Token cleanup cannot delete or release the operation ID. Its independent minimal tombstone does not rely on any Token foreign key, cascade or continued challenge row. A tombstone returns a neutral fail-closed result and cannot prove a request matches. Account closure or deletion must not release it. If governing privacy or legal authority later requires its removal, reconcile that conflict before any operation-ID reuse becomes possible.

Identity's minimum restricted audit evidence for each accepted resend is its operation ID, safe account reference while retention permits, source/purpose classification, accepted result class and acceptance timestamp. A safe challenge identifier or intent identifier may be retained only when needed for correlation and authorised by the applicable retention policy; neither confers authority or requires the referenced row to survive. No provider status, delivery attempts, destination or message content is copied. The accepted assertion is immutable while retained. Correction is separately attributable and does not overwrite it. Retain this evidence independently of Token lifecycle for the approved audit category and any valid hold, then dispose or anonymise according to that policy; the non-identifying operation tombstone remains. Access is deny-by-default, purpose-limited and through Identity's scoped owner interface.

No raw verification bearer, decrypted capability, encryption material, rendered body, secret-bearing URL, password, raw request or equivalent protected material may enter the operation, tombstone, audit, logs or telemetry. Request fingerprints and key metadata are restricted comparison material, not audit fields, and are cleared at tombstoning. Logs and metrics use bounded result classes without operation IDs or personal identifiers.

## Framework and proof

USE: Ash Resource, purpose-specific actions and policies for the owner boundary; Ash identities and AshPostgres/PostgreSQL unique and check constraints for durable ID and state invariants; a shared PostgreSQL transaction and row locking or equivalent conditional database arbitration for acceptance. Verify the exact supported APIs and same-Repo transaction participation at WELL-51 implementation time. AshAuthentication Token remains proof authority and its expunger must not govern resend retention. The existing locked stack is Ash 3.37.2, AshPostgres 2.15.2 and AshAuthentication 4.15.0; no dependency is added here. Version-matched primary references: [Ash Resource DSL](https://hexdocs.pm/ash/3.37.2/dsl-ash-resource.html), [AshPostgres data-layer DSL](https://hexdocs.pm/ash_postgres/2.15.2/dsl-ashpostgres-datalayer.html), and [AshAuthentication Token Resource](https://hexdocs.pm/ash_authentication/4.15.0/AshAuthentication.TokenResource.html). These establish the relevant actions, identities, transaction options, constraints and Token cleanup facilities, not proof of the composed transaction.

NOT APPLICABLE: Signals for atomic acceptance or durable truth; asynchronous reactions cannot replace the shared transaction. Temporal Resources for a live binding and tombstone with no as-of requirement. StateMachine for two states whose guarded transitions fit ordinary Ash actions. PaperTrail/history tooling for the minimum immutable accepted assertion, which the purpose-specific Resource already owns. DEFER exact action syntax, fingerprint construction, locks, indexes and retention policy to implementation and the relevant policy owner; none changes the semantic contract.

WELL-51 proof must exercise same-ID matching and changed inputs concurrently, two distinct competing IDs, an old replay after a later accepted resend, Token cleanup before replay and after tombstoning, failure at every acceptance consequence, restart, closure/invalidation races, access denial and secret redaction. Prove one active challenge, one intent and envelope per accepted operation, no central resend Audit obligation or schedule, and permanent non-rebinding. Prove the shared transaction against the actual selected Ash/AshPostgres APIs and data layer; this document is not executable proof.
