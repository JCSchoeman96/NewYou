## Purpose and current boundary

P8-05 is the first production-path Phase 8 proof slice. Its bilingual browser path presents approved launch and safety content before registration and enforces the required 18+ and exact Terms/Privacy acceptance gates before Account creation. The TB-001 PostgreSQL acceptance transaction commits one Identity-owned Account with an active password credential and its hash, its canonical active PMR, a verification Token, the selected Audit EvidenceObligation, a Communications MessageIntent, and both required owner-specific initial durable scheduling consequences: Communications delivery scheduling reconstructable from `MessageIntent.id` and Audit E2 materialisation scheduling reconstructable from `EvidenceObligation.id`. Password validation, Account creation, credential activation, and password-hash establishment are one accepted Identity transition. Raw passwords are never persisted.

The Account remains unverified and has no Session. The participant sees a localized verification-pending page. P8-05 does not consume verification proof, log the participant in, execute Communications or Audit durable workers, contact a provider, or certify the full TB-001 proof.

## Accepted WELL-46 protected-delivery mechanism

Security/Architecture accepted this mechanism for P8-05. PR #148 merged certified head `afe371bc996af166b104728960b53b8369371034`. Its merge/live-main SHA is `23e9567014c43898e083a5b7d1495086fdec64bc`. WELL-46 is canonically resolved. The protected-delivery mechanism below remains exactly as recorded; this status update changes no WELL-46 semantics and does not authorize implementation. WELL-45 is a separate legal/privacy release gate; it no longer blocks development that satisfies the explicit development-baseline and P8-05 gates below.

Use a private PostgreSQL authenticated-encryption envelope, bound one-to-one to a Communications `MessageIntent`. The envelope is sensitive delivery machinery. Private implementation-only PostgreSQL storage is permitted; the envelope is not a new Domain, Ash business Resource, Identity verification record, Communications delivery-attempt record, or second token/challenge store. Keep it in the same PostgreSQL Repo and transaction as the required acceptance consequences. Its only purpose is to preserve the bearer already issued for an already-authorized communication across process or node failure and durable retry. Row presence does not grant send authority.

Identity remains the sole authority for challenge purpose, validity, expiry, supersession, revocation, and consumption. Communications remains the sole authority for `MessageIntent`, `DeliveryAttempt`, delivery admission, provider-delivery lifecycle, and durable delivery scheduling. Communications owns the private, purpose-scoped capability writer and reader because the envelope exists only for delivery. The issuance/orchestration path invokes the Communications-owned capability writer through Communications' owner interface. Communications must use Identity's current non-secret eligibility result and cannot decide whether an Identity challenge remains valid. This mechanism creates no shared-write ownership.

At rest, store only the authenticated ciphertext containing the bearer, its unique `MessageIntent.id` association, the corresponding durable Identity source reference and purpose, a non-secret key version, and the nonce and authentication data required by the chosen AEAD representation. A copied source expiry may be stored only when it helps bound cleanup. Do not copy a token fingerprint, Identity validity or lifecycle state, destination, provider-attempt state, or delivery state. The implementation must enforce the one-to-one association. Associated data binds the immutable `MessageIntent.id`, Identity source reference, and purpose. It must not include duplicated mutable verification truth. If the implementation cannot reconstruct those values unambiguously at decryption, stop before coding and resolve the contract.

The accepted encryption direction is application-level AEAD using OTP `:crypto`, with AES-256-GCM as the current implementation candidate. Before coding, verify the exact API, key size, nonce generation and uniqueness requirements, authentication-tag handling, associated-data encoding, and error behavior against the supported Erlang/OTP version. AshCloak is not selected for this capability. Ash owner actions/interfaces, AshPostgres, and relevant Ash policies implement the existing business boundaries. AshOban/Oban may schedule and execute delivery only; they never store the bearer. Signals, Reactor, Temporal Resources, AshStateMachine, Archival, and PaperTrail are not part of protected-capability recovery.

Encryption keys are separate for each deployment environment. Keep them outside PostgreSQL, source control, committed configuration, and built release/container artifacts. Supply and validate them through the platform's runtime secret/configuration boundary. Store only the non-secret key version with each envelope. New envelopes use the active key. Earlier keys may remain decrypt-only during rotation and may be removed only after no live envelope or required retained recovery context depends on them. Rotation may re-encrypt live rows or let short-lived rows expire when safe. If a key is unavailable or compromised, fail closed. Do not fall back to plaintext, a default key, or a regenerated challenge. Identity owns any required challenge invalidation. Do not select a particular KMS or secret manager here.

For accepted initial registration, envelope creation commits in the same PostgreSQL acceptance transaction as the Account, PMR, credential and hash, Identity Token/challenge, accepted Terms and Privacy references, selected initial EvidenceObligation, MessageIntent, Communications schedule, and Audit schedule. A capability failure rolls back the accepted operation and leaves no recoverable orphan. For accepted resend, Identity's replacement/resend truth, the new MessageIntent, its envelope, and the Communications schedule commit or roll back together. The locked WELL-47 rule remains: resends create no central EvidenceObligation or Audit schedule. A committed transaction remains deliverable after process or node restart through the durable MessageIntent-ID-only schedule.

The durable job business payload / authoritative owner reference is only `MessageIntent.id`, encoded through AshOban's Resource primary-key envelope. The worker loads the MessageIntent through Communications, checks current Communications eligibility, resolves its Identity source reference and purpose server-side, obtains current non-secret Identity eligibility, admits the appropriate DeliveryAttempt, and only then retrieves the unique envelope by `MessageIntent.id` through the private Communications interface. The reader checks the source and purpose binding before decryption; the job never carries the source reference. No generic Ash read or ordinary application interface can return decrypted material. The worker then renders the participant-facing communication and submits it through the approved provider boundary. Missing, mismatched, expired, superseded, revoked, consumed, or cancelled authority fails closed. A worker never decrypts before current send authority and attempt admission are established.

Plaintext may exist only transiently in application memory in the narrow authorized delivery path needed to render and submit the verification message. It must not enter PostgreSQL plaintext, ordinary Identity or Communications fields, durable or general-purpose application coordination messages, durable jobs or their arguments or error payloads, unrelated process state, logs or Logger metadata, telemetry, traces/APM, crash reports, persisted exception details, Audit, Analytics, provider metadata, provider request logs, HTTP-client debug logs, LiveView/socket assigns, operator interfaces, committed test fixtures, or test failure output. Transient transport internal to the purpose-scoped provider-delivery stack may occur where required by the selected client, but it must remain bounded to that delivery operation and must not become durable or observable application state. The provider request body containing the participant-facing verification link/message is the intended external disclosure boundary. Do not promise BEAM memory zeroization.

A conclusively safe retry may reuse the same envelope only after current Communications and Identity authorization passes again. A retry never creates another challenge, MessageIntent, or envelope, and never revives superseded material. An unknown or ambiguous provider outcome is not a retryable failure until Communications reconciliation permits another submission. If Identity invalidation wins before DeliveryAttempt admission, deny the send. If admission wins first, that already-admitted provider operation may finish under the existing Communications contract. The owning database transitions decide admission and cleanup races; process-local locks do not establish correctness. A later accepted resend makes the prior envelope unavailable for any new send; cleanup may follow idempotently. Provider acceptance alone does not require immediate deletion when a legitimate retry or reconciliation still needs the envelope.

Delete the live envelope when no legitimate retry or reconciliation needs it, and no later than the Identity source becoming expired, superseded, revoked, consumed, or cancelled, subject only to an already-admitted provider operation finishing under the cutover rule. Cleanup is idempotent; cleanup failure does not restore send authority. Ordinary PostgreSQL backup retention and expiry are accepted. Do not promise immediate cryptographic erasure from retained backups. After restore, keep outbound delivery blocked until current Identity authority, Communications state, suppression/current-policy state, and required reconciliation have been re-established. Revisit this mechanism only if a future Security/Privacy requirement demands immediate irrecoverability from backups.

Missing capabilities or schedules, unknown key versions, authentication/decryption failures, mismatched bindings, and orphan envelopes fail closed. Reconcile or quarantine them through the governed recovery path; never regenerate bearer material or manufacture business truth. Central Audit receives no bearer, ciphertext, key, secret-bearing URL, or duplicate delivery ledger. Existing selected accountability evidence may include safe identifiers and result classifications only where already governed.

## Registration and retry contract

Before the registration form, the participant chooses Afrikaans or English and receives applicable bilingual launch and safety content for that interaction locale. The same English governing Terms and Privacy documents are linked from both product experiences. Do not infer locale through an unreviewed fallback. In an explicitly permitted non-production environment/proof classification, the registration path may use the exact immutable English development-baseline Terms and Privacy IDs. A production-class or real-participant path requires exact legally/privacy approved English versions and fails closed otherwise. There is no environment fallback to a baseline legal version, latest lookup, default unapproved version, runtime legal translation or bypass while review is pending. Identity validates 18+ and acceptance gates; browser state alone is not authority. A failed age gate, absent acceptance, or context-ineligible legal version creates no Account or PMR. Record the exact Terms ID, exact Privacy ID, acceptance timestamp and participant interaction/preferred locale (af or en); legal document locale is en for both documents.

The complete required form data is first name, surname, email, authentication credential (password), preferred language, 18+ confirmation, and Terms/Privacy acceptance. The chosen Afrikaans or English locale supplies the preferred-language value stored on the Account. Identity validates the password before accepting registration, marks the password credential active, and establishes its hash on the Account in the same accepted transition. Invalid credentials and missing required fields reject before Account creation and leave no Account or PMR. The credential is stored only in the approved Identity password representation, never as raw password data. Phone and city are optional in DEC-027 and are not required for this proof.

The browser allocates an opaque ID before the first registration request. The proposed format is a random 128-bit UUIDv4 generated by a cryptographically secure browser source. The browser retains it for retries of that logical request and discards it after a terminal response. A changed form submission gets a new ID. The ID is an idempotency key, not a credential or proof of identity.

Identity treats the operation ID and request as one immutable pair. An identical retry after a committed acceptance returns the same neutral result without creating another business consequence. A request that reuses the ID with changed input is rejected without mutation. A failure before commit leaves no accepted operation and may be retried with the same unchanged request. A corrected request uses a new ID.

The accepted owner decision is a private Identity `RegistrationOperation` Resource, unique by opaque operation ID and exposed only through purpose-specific Identity actions. It is registration-idempotency machinery, not authentication, verification, credential, Account, Session, Communications, Audit, or generic operation-ledger authority. No public generic CRUD, direct Repo/Ecto persistence path, or new Domain is permitted. The browser operation ID is not a credential or proof.

The lifecycle is `absent → bound → tombstone`, with tombstone terminal. For each committed terminal operation, retain a versioned non-password request fingerprint, the slow password verifier and provider metadata needed to compare retries, neutral result category, nullable created-Account reference only when created by this operation, and commit/expiry times. The live binding expires 24 hours from authoritative database/server commit time; retries never extend expiry. Earlier invalidation clears the binding on applicable linked-Account password change/reset, closure/deletion, or explicit Security invalidation. Unrelated changes to a pre-existing Account do not invalidate a duplicate-email binding. At expiry/invalidation, remove fingerprint, key/provider versions, verifier, replay result and Account association; keep only opaque operation ID and the minimum fact needed to prevent rebinding. A tombstone has no participant lookup surface and cannot replay or authenticate.

For a new Account, the binding may retain the exact password hash bytes established for the new Account. For the duplicate-email terminal outcome, derive an operation-only slow verifier from the submitted password using the approved password-hash provider; never compare it to or copy the existing Account hash. The verifier serves only to compare same-operation retries, never login/reset/recovery/proof, and is removed with the live binding. Raw or recoverable passwords are never persisted. Account remains the sole credential authority.

Compute HMAC-SHA-256 over the canonical non-password request only. Use a dedicated environment-specific Identity registration-binding key, purpose-separated from all other platform keys and distinct from the WELL-46 delivery-encryption key. The key stays outside PostgreSQL, source control, committed config and built artifacts; provide it through the platform runtime secret-injection boundary. Store only its non-secret version while the binding is live. New bindings use the active key; previous keys are verification-only while a live binding references them and are removable once no live binding depends on them. Missing, invalid, unknown or unavailable key/provider material fails closed with no unkeyed/plaintext/default/current-Account fallback. Do not select a KMS/vendor here.

The fingerprint input is versioned, domain-separated and unambiguous (`registration-binding:v1`), with fixed field order, explicit types and length framing. It binds the operation ID and exact validated persisted non-password values: first name, surname, canonical email, preferred language/acceptance locale, 18+ confirmation, exact Terms and Privacy references, and any later field expressly included in this P8-05 request. Absent, empty, booleans, strings and identifiers remain distinguishable. Do not add Unicode normalization; do not include password, generated PMR/token IDs, timestamps or consequences. Password comparison is separate and uses exact registration credential input semantics.

Creation of a new Account and its RegistrationOperation binding commit inside the same authoritative PostgreSQL acceptance transaction. A valid duplicate-email terminal attempt also commits its own binding and neutral result, but creates no Account, PMR, Token, EvidenceObligation, MessageIntent, protected-delivery envelope or schedule. A pre-commit failure creates no accepted binding; the same unchanged request may retry with the ID, while corrected input uses a new ID. Identical live replays return the same neutral public result without rerunning consequences. Changed-input, expired, invalidated or tombstoned reuse rejects without mutation and without an account-existence signal. No public category or wording may reveal whether an Account exists; do not claim mathematically identical timing. PostgreSQL uniqueness and transaction semantics, not process-local locks or check-then-insert, arbitrate same-ID concurrency. Exact supported Ash/AshPostgres conflict and transaction APIs remain implementation-JIT verification. The browser ID never authorizes a read or mutation.

## Accepted WELL-48 owner decisions

Identity owns one email canonicalizer and a database uniqueness constraint. Identity and Product accepted this policy in the WELL-48 Grill. The syntax limits below are NewYou product policy informed by SMTP mailbox limits; they are not all SMTP requirements.

1. Strip only leading and trailing ASCII space (SP) and horizontal tab (HTAB). Reject other surrounding whitespace, all embedded whitespace, controls, and invisible Unicode whitespace.
2. Accept an ASCII dot-atom local part only. Reject quoted local parts, comments, display names, leading/trailing dots, consecutive dots and characters outside ASCII `atext`.
3. Accept an ASCII DNS domain with at least two labels. Each label is 1–63 ASCII octets, uses letters, digits and interior hyphens, and starts and ends with a letter or digit. Reject empty labels, leading/trailing hyphens, a leading or trailing dot, address literals and `xn--` labels until IDNA has a separately reviewed rule.
4. Enforce a local part maximum of 64 octets and a canonical mailbox maximum of 254 ASCII octets. The domain is at most 253 ASCII octets without a root dot. Registration validates syntax only; it does not depend on DNS lookup or transient DNS availability.
5. Reject every non-ASCII address input. SMTPUTF8 and Unicode-domain processing require a later Identity/Product review. No Unicode normalization is performed.
6. Preserve local-part bytes and case. Lowercase the ASCII domain. Preserve plus signs and dots; do not apply provider-specific alias rules.
7. Store and compare the resulting canonical value through Identity. The stored canonical email uses a deterministic, case-sensitive PostgreSQL text comparison. A unique database constraint on that value is the final concurrent-registration guard; application check-then-insert is not a correctness mechanism.

The canonicalizer contract should include fixtures equivalent to these examples:

| Input | Result |
|---|---|
| ` Alice+campaign.Example@EXAMPLE.COM ` | `Alice+campaign.Example@example.com` |
| `alice+campaign.Example@example.com` | Remains distinct from the preceding local-part because local-part case is preserved. |
| `Alice.Example+tag@example.com` | Dots and plus tag remain unchanged. |
| `"Alice Example"@example.com` | Rejected because quoted local parts are outside the accepted subset. |
| `alice@example.com` with a non-ASCII local or domain character | Rejected until SMTPUTF8/IDNA support has a reviewed rule. |

This is the accepted Identity/Product policy, not a complete rule dictated by SMTP. RFC 5321 requires preserving local-part case and says exploiting that distinction is discouraged. A provider that treats local-part case as insensitive may route two case variants to one mailbox even though Identity treats them as distinct. Case variants therefore remain distinct NewYou identities and may require participant support. The migration seam is explicit: later SMTPUTF8/IDNA support needs a new reviewed policy, a collision report against existing canonical identities, and an explicit account-resolution path. It must not silently merge or relabel existing Accounts.

The database constraint, rather than an application-level existence check, arbitrates simultaneous registrations for the same canonical email. Both the winner and duplicate-email terminal path use the neutral public response category and wording. Unique-constraint failures must be handled through the approved transaction mechanism without exposing account existence.

A distinct operation that loses the canonical-email uniqueness race returns the same public response as a newly accepted registration and creates no second Account, PMR, Token, EvidenceObligation, MessageIntent, Communications durable schedule, or Audit durable schedule. The new-account path and the duplicate path must have equal public response categories and wording in both locales. Timing and error mapping must not create an account-existence oracle.

## Approved PMR allocation contract

Identity approved this logical PMR representation for WELL-48 under `ARQ-IAM-013`. The physical allocation-history and database field/index representation remain implementation-JIT details:

```text
PMR-<16 Base36 data characters><1 ISO/IEC 7064 MOD 37,2 check character>
```

- Data alphabet: `0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ`.
- Check alphabet: `0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ*`.
- Canonical form: uppercase. Compute the ISO/IEC 7064 MOD 37,2 check character over `PMR` followed by the 16 data characters; exclude the presentation hyphen. Map `0–9` to values 0–9, `A–Z` to 10–35 and `*` to 36. The check value is `(38 - remainder) mod 37`, using the standard MOD 37,2 calculation. The check alphabet is `0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ*`.
- Generate the 16 data characters from a cryptographically secure source with unbiased Base36 mapping. The checksum adds no entropy.
- Space size: `36^16 = 7,958,661,109,946,400,884,391,936`, or about 82.72 bits. Approximate raw birthday collision probabilities before database retry are `6.3e-14` at 1 million allocations, `6.3e-12` at 10 million, `6.3e-10` at 100 million and `6.3e-8` at 1 billion. PMR is an identifier, not an authenticator.
- Identity maintains one concurrency-safe authoritative allocation history for active and retired PMRs. PostgreSQL uniqueness ultimately enforces non-reuse. Account closure, final deletion, merge, retirement and restore must preserve the reservation without retaining unnecessary personal association. A tombstone may retain the PMR only; no separate PMR Resource is introduced by this decision.
- Identity retries only genuine PMR uniqueness collisions, with a maximum of five generated candidates per allocation. Five is the accepted deterministic bound, not a value derived from the collision estimate. Any other persistence failure aborts the acceptance transaction. Exhaustion aborts safely and returns the same neutral temporary-failure category, with no PMR or account-existence detail. The implementation must verify a supported Ash/PostgreSQL retry mechanism rather than assume that a constraint error can be caught inside an aborted transaction.

Known check-character vector for the proposed mapping:

| Check input (hyphen excluded) | Displayed PMR | Expected check character |
|---|---|---|
| `PMR0123456789ABCDEF` | `PMR-0123456789ABCDEFA` | `A` |

The prefix `PMR` is a semantic identifier prefix, not a mutable public brand. The display hyphen is presentation only and is excluded from checksum input. The known vector is `PMR0123456789ABCDEF` → `PMR-0123456789ABCDEFA`, with check value 10 (`A`). ISO describes these systems as protection against human transcription errors, not deliberate falsification. This decision selects error detection, not secrecy or authenticity.

Identity's permanent non-reuse rule applies to active and retired PMRs across Account closure, final deletion, merge, reconciliation and database restore. A retired allocation may retain only the identifier reservation when privacy policy allows removal of its personal association. Collision correctness comes from the PostgreSQL uniqueness constraint, not probability or process-local locking.

## Atomic acceptance and scheduling

A successful initial registration commits all PostgreSQL business consequences in one authoritative transaction or commits none. The implementation must not establish the protected envelope outside the acceptance transaction as a fallback. Envelope-establishment failure rolls back the operation. If an orphan envelope is nevertheless discovered as an integrity fault, fail closed and reconcile or delete it. Orphan cleanup is recovery, not accepted transaction behaviour.

## Resend contract

The pending page exposes resend as a separate explicit action. The browser creates a resend operation ID for each click and reuses that ID only when retrying the same click.

For a valid new resend operation, Identity atomically supersedes the one active verification challenge and issues one replacement challenge. The same acceptance boundary creates exactly one MessageIntent and one Communications durable schedule whose only business payload / authoritative owner reference is `MessageIntent.id`. A retry with the same resend ID returns the prior result and creates no second challenge, intent, Communications schedule, EvidenceObligation, or Audit schedule. A later explicit click uses a new ID and may create one new replacement challenge, intent, and Communications schedule.

The accepted `WELL-47` decision is that an ordinary accepted resend is not selected as central E2. It creates no resend EvidenceObligation and no Audit durable schedule. The accepted resend boundary contains Identity's challenge replacement and resend audit, the new Communications MessageIntent and its durable schedule, and the protected delivery envelope specified above. The Communications job business payload / authoritative owner reference remains `MessageIntent.id` alone.

The response remains neutral for unknown, verified, expired, or otherwise ineligible accounts. Resend never creates a second Account or PMR. Identity owns the resend operation and its audit record; Communications owns the new MessageIntent and delivery schedule. This spec records the accepted `WELL-47` outcome but does not authorize implementation.

This slice does not consume the challenge, log in the participant, change the Account email, run delivery, or select rate limits. P8-07 owns scanner-safe consumption proof. OQ-035 continues to own abuse thresholds.
